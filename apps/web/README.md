# web

React 18 + Vite + TypeScript + Tailwind + shadcn/ui, installable as a PWA. Talks only to `jars-api` through the same origin (`/api/*`), so there is no CORS anywhere.

> **Origin.** The screens come from the hackathon prototype `ius_financial_ui`, which was mostly generated by Lovable. What this repository's author wrote is everything around them: Cognito sign-in (Authorization Code + PKCE), the typed API client generated from the backend's OpenAPI file, TanStack Query hooks, idempotent submissions, problem+json error handling, realtime notifications over SSE, and the tests.

## Run

```bash
npm ci
npm run dev        # http://localhost:5173, proxies /api and /dev to http://localhost:8080
npm test           # vitest, 119 tests
npm run lint
npm run build      # tsc + vite build + service worker
```

### Without Cognito (local development)

Start the backend with the `local` profile (see [local-development](../../docs/05-operations/local-development.md)) and put this in `.env.local`:

```
VITE_DEV_TOKEN_SUB=demo
```

The app then asks `POST /dev/token` for an access token of that subject and skips the login screen. This code path is removed from production builds. Add `--jars.seed.enabled=true` to the backend for three months of demo data.

### With Cognito

Fill `.env.local` from the CDK stack outputs (no value is a secret, the app client is public):

```
VITE_COGNITO_USER_POOL_ID=<JarsAuth UserPoolId>
VITE_COGNITO_CLIENT_ID=<JarsApp SpaClientId>
VITE_COGNITO_DOMAIN=<managed login domain without https://>
```

## How it fits together

| Folder | Role |
|---|---|
| `src/auth` | Amplify Auth v6 `signInWithRedirect`, session handling, protected routes, the dev-token mode |
| `src/api` | `openapi-fetch` client, middleware (bearer access token, 401 handling, problem+json to `ApiError`), one TanStack Query hook file per resource, idempotency keys, cursor paging |
| `src/realtime` | `fetch-event-source` on `/api/v1/notifications/stream` (the native `EventSource` cannot send an Authorization header), de-duplication by notification id, reconnect with `Last-Event-ID` |
| `src/lib` | Pure helpers with unit tests: money formatting, percentages, the onboarding questionnaire |
| `src/pages` | The screens |

Rules the code follows, because the backend depends on them:

- **Money is never a JS number.** The API sends `{ "amount": "85000.00", "currency": "VND" }`; it is parsed only for display.
- **One `Idempotency-Key` per user intent.** A form generates the key once and reuses it when the same submit is retried, so a double click or a retry after a network error posts exactly once.
- **Only the access token** is sent to the API, never the ID token.

## API types

`src/api/schema.d.ts` is generated from `contracts/openapi/jars-api.yaml`, which a backend test keeps equal to what the controllers produce:

```bash
npm run gen:api    # after the backend API changed
```

CI fails if the committed file differs from the generated one. Goals and budget types in `src/api/goals.ts` and `src/api/budget.ts` are derived from the generated schema through `DeepWire`, so a backend field change breaks `npm run typecheck`.
