## 2. Tại sao
- **Mỗi bước chỉ một mục tiêu**, nên chỉ thêm 3 starter. JPA, Modulith và AWS sẽ vào ở bước nào cần đến chúng. Thêm sớm thì app không khởi động được vì thiếu DB.
- **Hai loại health khác nhau:** `/api/v1/health` là hợp đồng công khai cho client và smoke test qua CloudFront (`/api/*`). `/actuator/health/*` dành cho hạ tầng (ALB, ECS) và không nên đưa ra ngoài internet.

## 3. Kiến thức cốt lõi
- **`@SpringBootApplication`** gồm `@Configuration` + `@EnableAutoConfiguration` + `@ComponentScan`. Scan bắt đầu từ package của class main (`io.github.thphuc06.jars`) và đi xuống các package con. Vì vậy `platform.web.HealthController` được tìm thấy mà không cần khai báo gì.
- **Auto-configuration chạy theo điều kiện.** Ví dụ `ProjectInfoAutoConfiguration` chỉ tạo bean `BuildProperties` **khi có** file `META-INF/build-info.properties`. Khi chạy bằng IDE mà chưa build qua Maven thì không có file đó. Vì thế controller dùng `ObjectProvider<BuildProperties>` (dependency tùy chọn) và fallback về `"dev"`, thay vì để app crash.
- **Liveness và readiness khác nhau:** liveness fail thì *khởi động lại container*; readiness fail thì *ngừng gửi traffic* nhưng giữ container. Nếu readiness kiểm tra DB, DB chập chờn sẽ kéo cả service xuống, và Aurora cũng không bao giờ pause được.
- **Virtual threads:** Tomcat dùng mô hình một thread cho mỗi request. Khi code chờ I/O (DB, Bedrock), virtual thread nhường carrier thread cho việc khác, nên chịu được hàng nghìn request đồng thời với code blocking dễ đọc. Từ JDK 24 (JEP 491), `synchronized` không còn làm virtual thread bị "pin" vào carrier thread.
- **Test slice và full context:** `@WebMvcTest` chỉ nạp tầng MVC (controller, converter, advice) nên nhanh và cô lập. `@SpringBootTest` nạp toàn bộ ứng dụng. `MockMvcTester` là API AssertJ mới của Spring 6.2+.

## 4. Cách khác & trade-off
| Lựa chọn | Trade-off |
|---|---|
| Dùng thẳng actuator làm health công khai | Ít code, nhưng lộ cấu trúc nội bộ và lẫn mục đích hạ tầng với mục đích client |
| WebFlux thay vì MVC + virtual threads | Reactive mạnh khi streaming nhiều, nhưng khó đọc, khó debug và không hợp với JPA (blocking) |
| `TestRestTemplate`/`RestTestClient` (HTTP thật) thay vì MockMvc | Sát thực tế hơn (chạy qua Tomcat) nhưng chậm hơn; dùng ở integration test sau này |
| Gradle | Build nhanh hơn, nhưng Maven phổ biến hơn trong JD ngân hàng |

## 5. Lỗi hay gặp
- **Copy code Boot 3:** `@WebMvcTest` đã chuyển sang `org.springframework.boot.webmvc.test.autoconfigure`, còn `@MockBean` đổi thành `@MockitoBean`. Starter `spring-boot-starter-web` giờ là `-webmvc`.
- **`include: "*"` cho actuator** làm lộ `/env` và `/heapdump`, tức lộ secret và bộ nhớ.
- **Đặt class main ở package con** khiến bean ở package khác không được scan.
- **Máy có 2 JDK:** `JAVA_HOME` trỏ vào 21 sẽ báo `release version 25 not supported`. Mở terminal mới rồi chạy `java -version` để kiểm tra.
- **`build.time=1980-02-01` trong build-info không phải bug.** Đó là *reproducible build*: Boot parent cố định timestamp để cùng source thì cho ra cùng JAR.

## 6. Câu hỏi phỏng vấn
1. *"Auto-configuration của Spring Boot hoạt động thế nào?"* Gợi ý: `AutoConfiguration.imports` liệt kê các class auto-config, mỗi class có các `@Conditional...` (`OnClass`, `OnMissingBean`, `OnProperty`). Bean bạn tự khai báo sẽ được ưu tiên vì có `@ConditionalOnMissingBean`.
2. *"Liveness khác readiness thế nào? Có nên check DB trong liveness không?"* Không: DB lỗi thì restart app cũng không sửa được, chỉ gây vòng restart vô tận.
