# P1.11a: Nền `apps/web`, đăng nhập PKCE với Cognito và client có kiểu

> Ghi chú học tập của bước P1.11a (2026-10-27). Kết quả và bối cảnh của bước nằm ở [roadmap](../06-plan/roadmap.md); quyết định ghi ở [ADR-0020](../04-adr/0020-spa-auth-oidc-client-ts.md); quy ước 7 mục ở [README](README.md).

## 1. Đã làm gì

| Phần | Nội dung |
|---|---|
| Tách bước | Đọc UI cũ trước khi code thì thấy **mô hình hũ khác hẳn**. UI cũ tự tạo/xóa hũ và mỗi hũ có `allocated/used/remaining`; mô hình mới có 6 hũ cùng `POOL`, số dư chỉ đổi qua giao dịch. Vì vậy logic từng màn phải viết lại. P1.11 được tách thành 3 lát dọc: **a** nền + đăng nhập, **b** Dashboard + Inbox, **c** Transfer + Jars + Goals |
| Chép UI kit | 49 component shadcn, layout, theme, PWA, trang Onboarding/Install/NotFound. **Bỏ lại** những file nguy hiểm hoặc vô dụng: `lib/supabase.ts` (anon key JWT và user id gõ cứng), `lib/auth.ts` (`USER_PASSWORD_AUTH` + client secret trong bundle), `lib/api.ts` (code chết), mock, `lovable-tagger`, ảnh OG trên R2 của Lovable, Google Fonts (chuyển sang tự host bằng `@fontsource`) |
| Toolchain | Vite 5 (bản vá cuối 10/2025) lên **8.3**; Vitest 4.1; `tsc` **strict** (cũ: `strict: false`, `strictNullChecks: false`), kit cũ vẫn qua được mà không phải sửa. React 18, Tailwind 3 giữ nguyên. `react-router` 6 lên 7 vì lỗ hổng open redirect. Gỡ `zod` và `@hookform/resolvers` vì không ai dùng |
| Supply chain | `.npmrc` `min-release-age=14`; cài và chạy CI với `--ignore-scripts`; cả 806 gói trong lockfile đều từ `registry.npmjs.org`; `npm audit` 0 lỗ hổng |
| Đăng nhập | `oidc-client-ts` + `react-oidc-context` (ADR-0020): Authorization Code + PKCE với managed login; token ở sessionStorage; tự làm mới bằng refresh token; logout thu hồi refresh token và gửi `client_id` + `logout_uri`; `RequireAuth` hiện màn đăng nhập (không tự chuyển hướng); `AuthCallback` theo flow F1 (chưa có hồ sơ rủi ro thì tới `/onboarding`); `safeReturnTo` chống open redirect |
| Client có kiểu | `gen:api` sinh `schema.d.ts` từ contract; `api:check` fail khi lệch. `openapi-fetch` + middleware gửi **access token**; `unwrap` chuyển lỗi thành `ApiError` có `status`, `code`, `problem.traceId` |
| Màn hình | Onboarding gửi `PUT /me/risk-profile` (5 câu khớp 1:1 với enum, server chấm điểm); Profile viết lại với `GET /me` và risk profile; các màn còn lại hiện "chuyển ở P1.11b/c" |
| CI | Job `web`: `npm ci --ignore-scripts` → `api:check` → lint → typecheck → test → build |

**Bằng chứng:**

| Kiểm tra | Kết quả |
|---|---|
| Probe Cognito thật (chỉ GET) | Đúng `redirect_uri` + S256 → trang login; sai cổng → `redirect_mismatch`; `offline_access` → `invalid_scope`; logout với `post_logout_redirect_uri` (chuẩn OIDC) → **bị bỏ qua** (hiện trang login); với `client_id` + `logout_uri` → 302 về app; `logout_uri` lạ → không chuyển hướng |
| Bundle phần auth (esbuild, minify) | Amplify Auth 30,7 kB vs `oidc-client-ts` + `react-oidc-context` 19,3 kB gzip |
| Test web | **25** test; **6/6 mutant** bị bắt: bỏ kiểm tra `\` trong `returnTo`, client giữ `fetch` cũ, callback gọi API khi chưa có token, gửi ID token, đổi 2 đáp án cho nhau, logout bằng tham số chuẩn OIDC. Mutant số 3 lúc đầu **sống sót**, do test có lỗi (mục 5) |
| Tích hợp với backend thật | Qua proxy của Vite: `/api/v1/health` 200; `/api/v1/jars` không token → 401 ProblemDetail + `traceparent`; `/auth/callback` trả về SPA |
| Tiền dạng string | `formatVND("12345678901234567.00")` = `…567 ₫`; `formatVND(Number(...))` = `…568 ₫` |
| Build | JS 472 kB (146 kB gzip), CSS 14 kB gzip; font tách theo subset, kể cả tiếng Việt |
| CI mô phỏng (cài sạch) | Cả 5 bước đạt |

## 2. Tại sao

- **UI cũ không an toàn mà cũng không đúng.** Mật khẩu đi qua code của app, client secret nằm trong bundle JS (ai mở DevTools cũng thấy), mọi người dùng chung một user id gõ cứng. Đây không phải chuyện "đổi URL API" là xong.
- **Chép giao diện, viết lại logic.** Kit shadcn và layout là phần giá trị và đã chạy tốt. Tầng data và auth là chỗ cũ sai, nên viết lại hoàn toàn.
- **Lát dọc thay vì làm hết rồi mới chạy.** P1.11a chứng minh cả chuỗi chạy được: đăng nhập → token → client có kiểu → API thật → ghi DB (Onboarding). Các bước b và c chỉ còn thêm màn hình trên nền đã chạy.

## 3. Kiến thức cốt lõi

| Khái niệm | Ý chính |
|---|---|
| Authorization Code + PKCE | SPA là **public client**, không giữ được secret. PKCE thay secret bằng một bí mật dùng một lần: app sinh `code_verifier` ngẫu nhiên, gửi `code_challenge = BASE64URL(SHA-256(verifier))` lúc authorize, rồi gửi `verifier` lúc đổi code lấy token. Kẻ lấy được `code` (qua log, lịch sử trình duyệt) không có `verifier` nên không đổi được |
| `state` và `nonce` | `state` chống CSRF ở bước callback và mang theo `returnTo`; `nonce` gắn ID token với đúng lần đăng nhập. `oidc-client-ts` tự sinh và tự kiểm cả hai |
| Access token vs ID token | ID token mô tả user **cho client**; access token dùng để **gọi API**. jars-api từ chối ID token (`token_use`). Middleware chỉ gửi access token, và có test chứng minh |
| Nơi lưu token | Bộ nhớ (mất khi reload), sessionStorage (theo tab), localStorage (lâu, chung mọi tab), cookie HttpOnly qua BFF (JS không đọc được). Ba lựa chọn đầu đều đọc được khi có XSS; khác nhau ở **thời gian và phạm vi** bị lộ |
| Open redirect | `navigate(returnTo)` với `returnTo = "//evil.example"` (URL tương đối giao thức) hoặc `"/\evil.example"` (trình duyệt đọc `\` như `/`) sẽ đưa người dùng sang site khác sau khi đăng nhập, rất hợp để phishing. Chỉ nhận đường dẫn bắt đầu bằng **một** `/`, không có `\` |
| Same origin + proxy | Vite proxy `/api` → `:8080`; CloudFront sẽ làm việc tương tự. Không có CORS, không có preflight cho header `Authorization`/`Idempotency-Key`, và cookie (nếu sau này dùng BFF) không cần `SameSite=None` |
| Supply chain npm | Lockfile ghim **version chính xác** + `npm ci`. `--ignore-scripts` chặn script `postinstall`, đường tấn công phổ biến nhất. `min-release-age` né các bản phát hành bị chiếm quyền, vốn thường bị phát hiện và gỡ trong vài ngày |

## 4. Cách khác và trade-off

| Cách | Ưu | Nhược |
|---|---|---|
| **`oidc-client-ts` + sessionStorage** (đã chọn) | OIDC chuẩn, dùng được với mọi IdP; nhỏ hơn; tự kiểm soát nơi lưu và cách logout | Phải tự xử lý 2 điểm riêng của Cognito (đã test) |
| Amplify Auth | Hiểu sẵn Cognito; có Amplify UI | Gắn với hệ Amplify; mặc định localStorage; lớn hơn khoảng 11 kB gzip |
| BFF + cookie HttpOnly | XSS không đọc được token; IETF khuyên dùng cho SPA | Thêm một tầng server, phải chống CSRF; để làm sau |
| Tự động chuyển tới trang login khi chưa đăng nhập | Ít hơn một lần bấm | Đăng nhập lỗi (người dùng bấm hủy) có thể tạo vòng lặp chuyển hướng vô tận |
| Nâng luôn React 19 + Tailwind 4 | Bản mới nhất | Phải sửa 49 component kit; không liên quan tới mục tiêu của bước này |
| `--legacy-peer-deps` để dùng `@vitejs/plugin-react` | Bundle nhanh hơn một chút | Nhắm mắt chấp nhận Babel 7 và 8 chạy lẫn nhau; lợi ích chỉ là tốc độ |

## 5. Lỗi hay gặp

1. **(Gặp thật)** Repo cũ có **anon key Supabase dạng JWT và user id gõ cứng**. Chỉ chép theo danh sách file đã chọn, sau đó quét lại (`grep` tìm `eyJ`, `supabase`, `lovable`, URL App Runner) và chạy gitleaks.
2. **(Gặp thật)** Cognito **bỏ qua** `post_logout_redirect_uri`. Logout có vẻ chạy nhưng người dùng bị kẹt ở trang login của Cognito. Phải dùng `logout_uri` + `client_id`.
3. **(Gặp thật)** `min-release-age` **chặn luôn bản vá bảo mật**: 4 bản sửa lỗi đều mới 5–12 ngày, nên `npm audit fix` không làm gì. Cách xử lý là cho đi tắt có chủ đích (`--min-release-age=0` chỉ cho lệnh audit fix), giống Dependabot và Renovate.
4. **(Gặp thật)** `openapi-fetch` **giữ cố định** `globalThis.fetch` lúc `createClient`, nên test stub `fetch` sau đó không có tác dụng. Cách sửa: `fetch: (r) => globalThis.fetch(r)`. Một lỗi liên quan: `Request` của Node không nhận URL tương đối, nên base URL phải là `location.origin`.
5. **(Gặp thật)** Test "không gọi API khi chưa có token" **luôn xanh, kể cả khi code sai**. Nó assert ngay sau `render`, trong khi query chạy trong effect và middleware còn `await getUser()` trước khi gọi `fetch`. Chỉ lộ ra khi chạy mutant. Muốn kiểm tra "không xảy ra" thì phải cho các tác vụ bất đồng bộ chạy xong trước.
6. Gọi API trên trang callback **trước khi** đổi code lấy token → 401. Dùng `enabled: auth.isAuthenticated`.
7. Chạy Vite ở cổng 8080 như UI cũ: trùng cổng backend, và Cognito báo `redirect_mismatch` vì callback đã đăng ký là `:5173`. Dùng `strictPort: true`.
8. Chuyển tiền sang `Number` để hiển thị thì mất chữ số khi vượt 2^53. `Intl.NumberFormat` định dạng **string** chính xác.
9. **(Gặp thật)** Định commit `.env.development` (giá trị không bí mật) thì phát hiện `.gitignore` gốc **cố ý** chặn mọi `.env.*`. Mình không mở ngoại lệ cho một rule bảo vệ: giá trị test chuyển vào `test.env` của Vitest, còn giá trị dev nằm ở `.env.local` trên máy, được tạo từ `.env.example`.

## 6. Câu hỏi phỏng vấn

1. Vì sao SPA không được dùng client secret? PKCE giải quyết vấn đề gì, và khác `state` ở đâu?
2. Lưu access token ở đâu trong SPA? So sánh memory, sessionStorage, localStorage và BFF với cookie HttpOnly.
3. Access token và ID token khác nhau thế nào? Gửi nhầm ID token lên API thì sao?
4. Open redirect là gì? Vì sao `//evil.com` vượt qua được kiểm tra `startsWith("/")`?
5. Có những cách nào phòng tấn công supply chain trong npm? `npm ci` khác `npm install` thế nào?
6. Làm sao để test được rằng một việc **không** xảy ra trong code bất đồng bộ?
7. Vì sao cho frontend và API dùng cùng origin (proxy hoặc CloudFront) thay vì bật CORS?

## 7. Bài tập nhỏ

1. Đăng nhập thật trên `http://localhost:5173` bằng user của pool dev. Mở DevTools → Application → Session Storage và tìm key `oidc.user:...`; decode access token trên jwt.io (hoặc bằng `atob`). Có claim `scope` nào, `token_use` là gì? Mở một tab mới: có phải đăng nhập lại không, và có phải gõ mật khẩu không?
2. Đặt `accessTokenValidity` là 5 phút (chỉ thử ở dev, rồi trả về như cũ), mở tab Network và xem `oidc-client-ts` gọi `/oauth2/token` với `grant_type=refresh_token` lúc nào. Sau khi logout, gửi lại đúng request refresh đó bằng `curl`: Cognito trả gì?
3. Viết thêm test cho `safeReturnTo` với `"/%2F%2Fevil.example"` và `"/\t/evil.example"`. Trình duyệt xử lý chúng thế nào khi điều hướng? Hàm hiện tại có cần sửa không?
