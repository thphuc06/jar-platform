# P1.1: Hạ tầng bằng CDK Java + Cognito (PKCE)

> Ghi chú học tập của bước P1.1 (2026-10-23, commit `f046148`). Kết quả và bối cảnh của bước nằm ở [roadmap](../06-plan/roadmap.md); quy ước 7 mục ở [README](README.md).

## 1. Đã làm gì
- Tạo [infra/cdk](../../infra/cdk): CDK viết bằng Java, CLI được ghim version, có launcher chạy được trên mọi hệ điều hành, và 7 test hạ tầng.
- Chạy `cdk bootstrap` cho ap-southeast-1, rồi **deploy stack `jars-dev-auth`** gồm user pool, managed login, resource server `jars-api` (read/write) và app client dùng PKCE.
- Kiểm tra bằng request thật:

| Kiểm tra | Kết quả |
|---|---|
| OIDC discovery + JWKS (2 key) | ✅ |
| Request PKCE hợp lệ → trang login | ✅ HTTP 200 |
| `redirect_uri` lạ | ✅ bị chặn (`redirect_mismatch`) |
| Implicit flow | ✅ bị từ chối |

## 2. Tại sao
Từ P1.2, Spring cần một issuer thật để xác thực JWT. Cognito ở quy mô này miễn phí, nên deploy sớm không tốn gì, và dev ở local vẫn dùng token thật.

## 3. Kiến thức cốt lõi
- **Bỏ trống khác với khai báo rỗng:** `AuthFlow.builder().build()` sinh ra template **không có** `ExplicitAuthFlows`, và khi đó Cognito **tự bật** cả `CUSTOM_AUTH`. Tôi chỉ phát hiện ra nhờ đọc template đã synth. Bây giờ đã có test khóa lại.
- **PKCE:** SPA không giữ được bí mật. PKCE dùng một cặp `code_verifier`/`code_challenge` sinh ngẫu nhiên cho từng lần đăng nhập, để authorization code bị đánh cắp cũng không đổi được ra token.
- **Kiểm tra `redirect_uri` theo danh sách cho phép** là lớp bảo vệ chính của OAuth2. Thiếu nó, kẻ tấn công lừa người dùng đăng nhập rồi nhận code về trang của mình.
- **cdk-nag v3** dùng API `Validations` có sẵn của CDK. Mỗi vi phạm được acknowledge phải kèm lý do. Tôi **chỉ** acknowledge những gì cdk-nag thật sự báo (COG8, COG2), không acknowledge "phòng hờ".

## 4. Cách khác & trade-off
| Cách | Trade-off |
|---|---|
| Terraform | Phổ biến hơn trong JD, nhưng thêm một ngôn ngữ và phải tự quản lý state; CDK Java giúp luyện Java luôn ([ADR-0012](../../docs/04-adr/0012-iac-aws-cdk-java.md)) |
| Tạo Cognito bằng tay trên console | Nhanh, nhưng không tái lập được, không review được, không test được |
| Gói Plus (có threat protection) | An toàn hơn nhưng tính phí theo MAU |

## 5. Lỗi hay gặp
- Tin rằng builder rỗng nghĩa là "tắt hết" (lỗi auth flow ở trên).
- Dùng code cdk-nag v2 (`NagSuppressions`) với bản v3 → không compile được.
- `cdk.json` gọi `mvnw` trên Windows khi thiết lập `NoDefaultCurrentDirectoryInExePath` đang bật → không tìm thấy lệnh.
- Bật implicit flow cho SPA, khiến token nằm lộ trên URL.

## 6. Câu hỏi phỏng vấn
1. *"Authorization Code + PKCE khác implicit flow thế nào? Vì sao SPA không được giữ client secret?"*
2. *"Access token khác ID token thế nào? API nên nhận loại nào?"*
3. *"Làm sao kiểm thử hạ tầng viết bằng code?"* Trả lời: test assertion trên template, rule cdk-nag, và kiểm tra thật sau khi deploy.

## 7. Bài tập nhỏ
Viết thêm một test trong `AuthStackTest` chứng minh **không có** client nào có `GenerateSecret: true`. Gợi ý: dùng `findResources`. Sau đó đổi `localWebOrigin` thành `http://localhost:3000` bằng `-c`, chạy `npx cdk diff JarsAuth` (chỉ xem, **đừng** deploy) và đọc xem CloudFormation sẽ thay đổi những gì.
