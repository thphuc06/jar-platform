# P1.4: Module ledger + outbox (event registry của Spring Modulith)

> Ghi chú học tập của bước P1.4 (2026-10-26, commit `e17f916`). Kết quả và bối cảnh của bước nằm ở [roadmap](../06-plan/roadmap.md); quy ước 7 mục ở [README](README.md).

## 1. Đã làm gì

| Phần | Nội dung |
|---|---|
| Dependency | Đổi `spring-modulith-starter-core` thành `spring-modulith-starter-jdbc`. Bản mới gồm core, phần lưu event và serializer Jackson |
| Flyway V2 | Bảng outbox `event_publication`, chép nguyên file DDL v2 chính thức trong jar `spring-modulith-events-jdbc` 2.1.2 |
| Flyway V3 | Bảng `jars` và `categories`. Các quy tắc BR-1/2/3 được DB chặn bằng `CHECK`, unique index một phần (`WHERE code <> 'CUSTOM'`) và `NULLS NOT DISTINCT`. Seed sẵn 15 danh mục hệ thống với id cố định |
| Module `ledger` | `Jar`, `Category`, `JarCode`, `DefaultJars` (BR-1), và `DefaultJarsProvisioner` dùng `@ApplicationModuleListener(id = "ledger.default-jars")` |
| Ranh giới module | `allowedDependencies = {"identity", "shared"}`. Đã cố tình vi phạm thử và build fail đúng như mong đợi |
| `UserRegistered` | **Bỏ `email`** khỏi event (lý do ở mục 2) |
| Test (+20) | Unit BR-1; 10 test constraint DB; query `findVisibleTo` không trả danh mục của người khác; module test dùng `Scenario` (tạo hũ, xóa dòng outbox, event đến 2 lần, listener lỗi rồi gửi lại); test F1 giờ chờ thấy đủ 7 hũ, kể cả khi 8 luồng chạy cùng lúc |
| Docs | data-model, modules, event-catalog, flows F1, ghi chú trong ADR-0009, roadmap |

**Ba chỗ lệch so với kế hoạch** (đã ghi trong roadmap):
- Lưu event bằng **JDBC** thay vì JPA.
- `JarEntry` dời sang P1.5, vì nó cần FK tới `transactions` và lần đầu được dùng ở đó.
- Id của entity sinh bằng `shared.Ids` thay vì `@UuidGenerator`.

## 2. Tại sao

- **Outbox:** `identity` không gọi `ledger` mà chỉ phát `UserRegistered`. Event được ghi vào `event_publication` **trong cùng transaction** với dòng `users`. Vì vậy chỉ có 2 khả năng: hoặc có cả user lẫn event, hoặc không có gì. Không có trường hợp tạo được user mà mất event.
- **JDBC thay vì JPA:** bản JDBC có sẵn file DDL chính thức cho từng loại DB và từng version schema, nên Flyway sở hữu được bảng. Như vậy hợp với `ddl-auto=validate`, và khi nâng Modulith chỉ cần so sánh lại với file mới. Cả hai bản vẫn ghi chung transaction, vì `JpaTransactionManager` dùng chung connection.
- **Bỏ email khỏi event:** event được serialize thành JSON và lưu vào bảng outbox. Giữ email trong đó nghĩa là chép PII sang một bảng thứ hai. Listener nào thực sự cần email thì hỏi `IdentityApi`.
- **Chặn cả ở DB:** code Java có thể có bug, nhưng `CHECK` thì không bị bỏ qua. Ví dụ `balance >= 0` là lớp phòng thủ cuối cùng chống chi vượt số dư.

## 3. Kiến thức cốt lõi

| Khái niệm | Ý chính |
|---|---|
| `@ApplicationModuleListener` | Gồm `@TransactionalEventListener(AFTER_COMMIT)`, `@Async` và `@Transactional(REQUIRES_NEW)`. Log xác nhận listener chạy trên thread `task-N`, không phải thread request |
| Vòng đời một publication | Commit thì có dòng outbox. Listener chạy OK thì dòng bị xóa (`completion-mode=delete`). Listener lỗi thì dòng ở lại với `status=FAILED`, sau đó gửi lại bằng `FailedEventPublications.resubmit(...)` |
| At-least-once delivery | Event có thể đến 2 lần, nên listener phải **idempotent**: đã có hũ thì bỏ qua, và unique index `uk_jars_user_code` chặn thêm ở tầng DB |
| `id` cố định cho listener | Mặc định `listener_id` là tên method đầy đủ. Đổi tên class hoặc method thì các dòng đang chờ không còn khớp với listener nào và bị "mồ côi" |
| `@Version Long` (wrapper) | Id được gán trước khi lưu, nên Spring Data dựa vào `version == null` để biết entity mới và gọi `persist`. Nếu dùng `long` (kiểu nguyên thủy) thì nó gọi `merge`, tốn thêm một câu SELECT |
| Eventual consistency | `/me` có thể trả về **trước** khi 7 hũ xuất hiện, chậm khoảng vài chục ms. `GET /jars` ở P1.5 phải xử lý trường hợp này |

## 4. Cách khác và trade-off

| Cách | Ưu | Nhược |
|---|---|---|
| **Async listener + outbox** (đã chọn) | 2 module tách rời; listener lỗi không làm đăng ký user thất bại; event không mất | Eventual consistency; phải lo idempotency và việc gửi lại |
| `@EventListener` đồng bộ, cùng transaction | Tạo user là có hũ ngay | Ledger lỗi kéo theo đăng ký user lỗi; 2 module bị nối chặt về transaction |
| `identity` gọi thẳng `LedgerApi.createDefaultJars()` | Đơn giản, dễ đọc | `identity` phụ thuộc `ledger`, trong khi đồ thị thiết kế đi chiều ngược lại, nên sẽ thành vòng phụ thuộc |
| Bản lưu JPA | Không cần SQL tay | Không có DDL chính thức; Hibernate tự validate theo entity của Modulith |
| `completion-mode=update` hoặc `archive` | Giữ lịch sử event | Bảng phình dần; lịch sử nên nằm ở log hoặc trace, không nằm ở outbox |

## 5. Lỗi hay gặp

1. **Quên bật async:** nếu không có `@EnableAsync` thì `@Async` bị bỏ qua mà không báo lỗi. Modulith có `AsyncEnablingConfiguration` lo việc này, và mình đã xác nhận qua tên thread trong log.
2. **Listener không idempotent:** khi gửi lại sẽ sinh 14 hũ.
3. **Cột `CHAR(3)` map vào `String`:** schema validation đòi `VARCHAR` nên app không khởi động được. Đã xử lý bằng `@JdbcTypeCode(SqlTypes.CHAR)`.
4. **Unique index có cột NULL:** mặc định PostgreSQL coi hai giá trị NULL là khác nhau, nên 2 danh mục hệ thống trùng tên vẫn lọt qua. Phải dùng `NULLS NOT DISTINCT`, chỉ có từ PostgreSQL 15.
5. **So sánh `BigDecimal` bằng `equals`:** `100` khác `100.00` theo `equals`. Phải dùng `compareTo` hoặc `isEqualByComparingTo`.
6. **Test async chỉ đúng nhờ may mắn:** assert ngay sau khi publish thì đôi khi pass, đôi khi fail. Phải chờ bằng `Scenario.andWaitForStateChange` hoặc Awaitility.
7. **MDC không đi theo sang thread khác:** log của listener có `traceId` rỗng. Đây là thiếu sót đã biết, đưa vào P2.1.

## 6. Câu hỏi phỏng vấn

1. Transactional outbox giải quyết vấn đề "dual write" nào? Nếu publish thẳng lên SNS bên trong `@Transactional` thì hỏng ở đâu?
2. `@TransactionalEventListener` khác `@EventListener` thế nào? Nếu không có transaction đang chạy thì chuyện gì xảy ra?
3. At-least-once và exactly-once khác nhau ra sao? Làm thế nào để consumer idempotent?
4. Vì sao `@Async` hoặc `@Transactional` không có tác dụng khi gọi method trong cùng một class?
5. `persist` và `merge` khác nhau gì? Spring Data `save()` quyết định gọi cái nào ra sao?
6. Khi chạy nhiều instance, bật "republish on restart" sẽ gây vấn đề gì?
