# P3.1: Container image cho Fargate và AOT cache của JDK 25

> Ghi chú học tập của bước P3.1 (2026-10-27), bước đầu của Phase 3 (làm trước Phase 2, xem [roadmap](../06-plan/roadmap.md)). Quy ước 7 mục ở [README](README.md).

## 1. Đã làm gì

| Phần | Nội dung |
|---|---|
| [Dockerfile](../../apps/jars-api/Dockerfile) | 3 stage. **build**: JDK 25, `mvnw package` với Maven repo trong BuildKit cache mount, tách jar thành layer (`app.jar` + `lib/`). **runtime**: JRE 25 (Ubuntu noble) **ghim theo digest**, 4 layer theo tần suất thay đổi, UID `10001`, `ENTRYPOINT` dạng exec. **aot**: runtime + một training run tạo AOT cache |
| JVM trong container | `-XX:MaxRAMPercentage=75` (heap tính theo giới hạn RAM của task), `-XX:+ExitOnOutOfMemoryError`, `-XX:-UsePerfData` (không ghi `/tmp/hsperfdata`), `-XX:+UseSerialGC` ghi rõ |
| Graceful shutdown | `server.shutdown: graceful` + `spring.lifecycle.timeout-per-shutdown-phase: 20s` (nhỏ hơn `stopTimeout` 30 s của ECS) |
| AOT cache (JEP 514/515) | `java -XX:AOTCacheOutput=app.aot -Dspring.context.exit=onRefresh -jar app.jar` với một Postgres tạm; mật khẩu qua `--secret`. Training thất bại thì build fail |
| CI | Job `jars-api-image` trên runner **`ubuntu-24.04-arm`**: build, kiểm tra kiến trúc arm64, user, `java -version` |
| Research Phase 3 | CDK giữ 2.273.0; đọc Terraform cũ (x86_64, ALB public, `/health` tự viết...), xem roadmap |

**Bằng chứng (container 0.5 vCPU / 1 GB, `--read-only`, `/tmp` tmpfs):**

| Kiểm tra | Kết quả |
|---|---|
| Khởi động, 3 lần mỗi loại | Image thường **21,8 / 21,6 / 21,4 s**; AOT cache **10,2 / 10,3 / 10,3 s**; log `[aot] Opened AOT cache app.aot` |
| Trên máy dev (không giới hạn CPU) | 4,9 s → 2,05 s |
| Bảo mật container | `id` = `uid=10001`; ghi vào `/app` → `Read-only file system`; `/tmp` ghi được |
| SIGTERM (`docker stop`) | Dừng trong **0,77 s**, exit code **143**; log: Tomcat graceful → outbox Modulith "No publications outstanding" → JPA → Hikari |
| Kích thước | Image nén 159 MB (thường) / 193 MB (có AOT cache); JRE 201 MB, dependencies 72 MB, **`app.jar` 0,25 MB** |
| Mật khẩu training | Không có trong `docker history` (0 lần xuất hiện) |
| Training với DB sai | `docker build` fail với exit code 1 |
| Build cho arm64 (Graviton) trên máy x86_64 | `docker buildx build --platform linux/arm64` qua QEMU mất **179 s**; container báo `uname -m` = `aarch64`, JVM chạy được. CI dùng runner arm64 thật nên không phải giả lập |
| RAM sau khởi động | Khoảng 300 MiB (thường), 270 MiB (AOT) trên 1 GiB |

## 2. Tại sao

- **Fargate tính tiền theo vCPU và RAM mỗi giây**, nên task phải nhỏ (0.5 vCPU / 1 GB). Với 0.5 vCPU, Spring Boot mất hơn 20 giây để khởi động, nên mỗi lần deploy hay scale-out đều phải đợi lâu. AOT cache cắt đôi thời gian đó mà không phải sửa code.
- **Image là thứ chạy trên production**, nên phải tối thiểu (chỉ JRE, không có Maven hay source), không chạy bằng root, không ghi được vào filesystem, và tái tạo được (ghim digest).
- **ECS dừng task bằng SIGTERM** rồi SIGKILL sau `stopTimeout`. Không xử lý graceful thì request đang chạy bị cắt ngang mỗi lần deploy.

## 3. Kiến thức cốt lõi

| Khái niệm | Ý chính |
|---|---|
| Multi-stage build | Stage build có JDK và Maven; stage cuối chỉ chép kết quả sang. Image cuối không chứa công cụ build (nhỏ hơn, ít CVE hơn) |
| Layer cache | Docker cache theo layer, từ trên xuống. Đặt dependencies (ít đổi) trước `app.jar` (đổi mỗi commit), nên mỗi lần deploy chỉ push khoảng 0,25 MB |
| BuildKit cache mount | `RUN --mount=type=cache,target=/root/.m2` giữ Maven repo giữa các lần build nhưng **không** đưa nó vào image |
| Ghim digest | `image:tag@sha256:...`: tag có thể bị đẩy bản mới, digest thì không. Nâng cấp thành một thay đổi được review |
| JVM trong container | JVM đọc giới hạn cgroup: `MaxRAMPercentage` chia heap theo RAM của task; với ít hơn 2 CPU hoặc dưới khoảng 1,8 GB RAM, JVM tự chọn SerialGC |
| PID 1 và tín hiệu | `ENTRYPOINT ["java", ...]` (exec form) thì java nhận SIGTERM. `sh -c "java ..."` thì shell là PID 1 và không chuyển tín hiệu, nên ECS phải chờ 30 s rồi SIGKILL. Exit 143 = 128 + 15 (SIGTERM) là bình thường |
| Read-only rootfs | Kẻ tấn công không ghi được file thực thi; app chỉ ghi vào `/tmp` (tmpfs). JVM mặc định ghi `/tmp/hsperfdata`, nên tắt bằng `-UsePerfData` |
| AOT cache (JDK 24+, Project Leyden) | Một lần chạy thử ghi lại các class đã nạp, đã link và profile; lần sau JVM map file cache vào thay vì đọc, kiểm tra và link lại từ jar. Cache chỉ dùng được với **cùng JDK, cùng kiến trúc, cùng classpath (dạng jar)** và các tùy chọn tương thích (GC, compressed oops) |
| `spring.context.exit=onRefresh` | Spring Boot khởi động tới khi context refresh xong rồi thoát: đủ để nạp gần hết class mà không phục vụ request nào |

## 4. Cách khác và trade-off

| Cách | Ưu | Nhược |
|---|---|---|
| **Dockerfile tự viết** (đã chọn) | Kiểm soát từng layer, user, flag; học được nhiều | Phải tự bảo trì |
| `spring-boot:build-image` (Buildpacks/Paketo) | Không cần Dockerfile, có sẵn CDS/AOT, SBOM | Image do builder quyết định, khó tùy biến; build cần Docker daemon và tải builder lớn |
| Jib | Không cần Docker daemon, layer tốt | Không có stage tùy ý (ví dụ training run) |
| Alpine (musl) | Nhỏ hơn khoảng 50 MB | musl khác glibc (DNS, hiệu năng); bản Temurin chính được build cho glibc |
| Distroless / jlink JRE tối giản | Nhỏ hơn, ít CVE hơn | Không có shell để debug; jlink phải liệt kê module |
| GraalVM native image | Khởi động dưới 1 s, RAM rất ít | Build lâu, reflection/proxy cần cấu hình; Hibernate/Modulith có thể vướng |
| Spring AOT (`process-aot`) | Không cần DB lúc build | Cải thiện ít hơn JVM AOT cache; có thể kết hợp sau |
| Không dùng AOT cache | Đơn giản, build không cần DB | Khởi động 21 s ở 0.5 vCPU |

## 5. Lỗi hay gặp

1. **(Gặp thật)** Tưởng app treo: `curl --retry-connrefused` dừng ngay với `000`, vì proxy cổng của Docker **nhận rồi reset** kết nối (không phải "connection refused") khi app chưa lắng nghe. Thread dump (`kill -3 1`) cho thấy JVM mới chạy 16 s và vẫn `RUNNABLE`. Dùng `--retry-all-errors`, và đọc thread dump trước khi kết luận.
2. **(Gặp thật)** Training run **thất bại vẫn tạo ra file `.aot`** (10 MB, rồi 76 MB). Phải kiểm tra exit code của training run, không chỉ kiểm tra sự tồn tại của file.
3. **(Gặp thật)** Tách jar với `--launcher` thì class được nạp qua classloader riêng của Spring Boot, cache không dùng được. Phải tách thành `app.jar + lib/`.
4. **(Gặp thật)** Training không có DB thì fail: Flyway, Hibernate (`ddl-auto=validate`) và Spring Modulith (dò loại DB cho outbox) đều mở kết nối lúc khởi động; Modulith 2.1.2 không có thuộc tính nào để khai báo sẵn loại DB.
5. Cache tạo trên máy build (nhiều CPU, G1) nhưng chạy trên task nhỏ (SerialGC) có thể bị **bỏ qua mà không báo lỗi**. Ghi rõ GC, rồi kiểm tra bằng `-Xlog:aot`.
6. Truyền mật khẩu bằng `ARG`: giá trị bị lưu trong `docker history` của image. Dùng `--secret`.
7. Image x86_64 chạy trên Graviton thì chết với `exec format error` (bản cũ ép `--platform=linux/amd64`).
8. Quên `-XX:MaxRAMPercentage`: Java hiện đại có hiểu cgroup, nhưng mặc định heap chỉ là 25 % RAM, lãng phí 1 GB đã trả tiền.

## 6. Câu hỏi phỏng vấn

1. Multi-stage build là gì? Vì sao image production không nên có JDK hay Maven?
2. Sắp xếp layer thế nào để build và push nhanh?
3. Vì sao container nên chạy non-root với root filesystem chỉ đọc?
4. Điều gì xảy ra khi ECS dừng một task? Graceful shutdown trong Spring Boot hoạt động thế nào? Exit code 143 nghĩa là gì?
5. JVM biết giới hạn RAM của container bằng cách nào? `MaxRAMPercentage` khác `-Xmx` ở đâu?
6. Làm sao giảm thời gian khởi động của Spring Boot (CDS/AOT cache, Spring AOT, GraalVM native, lazy init)? Trade-off của từng cách?
7. Vì sao ghim base image theo digest?

## 7. Bài tập nhỏ

1. Đổi `ENTRYPOINT` thành dạng shell (`ENTRYPOINT java -jar app.jar`), build lại, `docker stop` rồi đo thời gian: vì sao lâu đúng 10 s (mặc định của `docker stop`)? Log có còn "Graceful shutdown" không?
2. Bỏ `-XX:+UseSerialGC` khỏi cả hai chỗ, tạo lại image `aot`, chạy với `-e JDK_JAVA_OPTIONS=-Xlog:aot` trong container `--cpus 0.5 -m 1g`: cache có còn được dùng không? Đo lại thời gian khởi động.
3. Thử `./mvnw spring-boot:build-image` (Paketo) và so sánh kích thước image, thời gian khởi động và user chạy process với image của mình.
