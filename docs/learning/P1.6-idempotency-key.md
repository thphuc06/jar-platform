# P1.6: Idempotency-Key cho các POST làm thay đổi tiền

> Ghi chú học tập của bước P1.6 (2026-10-27, commit `7598037`). Kết quả và bối cảnh của bước nằm ở [roadmap](../06-plan/roadmap.md); quy ước 7 mục ở [README](README.md).

## 1. Đã làm gì

| Phần | Nội dung |
|---|---|
| Flyway V5 | Bảng `idempotency_keys`, khóa chính `(user_id, idempotency_key)`. Lưu `request_hash` (SHA-256), `response_body` (JSONB) và `expires_at` (24 giờ) |
| `IdempotencyStore` | Gắn `@Transactional(propagation = MANDATORY)`: chỉ chạy được **bên trong** transaction nghiệp vụ. Giữ chỗ key ở đầu transaction, lưu kết quả ở cuối |
| `PostingService` | Thứ tự lồng nhau: retry → transaction mới → **idempotency** → work. Số tiền được chuẩn hóa trước khi băm, nên `85000` và `"85000.00"` được coi là một request |
| API | Header `Idempotency-Key` bắt buộc (thiếu thì 400). Request lặp nhận lại **đúng body và `Location`** của lần đầu, kèm `Idempotent-Replayed: true`. Dùng lại key cho request khác thì 422 `idempotency-key-reused` |
| Test (+9) | Replay, chuẩn hóa số tiền, dùng lại key, dùng key ở endpoint khác, key riêng theo user, key hết hạn, thiếu header, request lỗi không được ghi nhớ. Thêm **8 luồng cùng một key: tiền chỉ bị trừ 1 lần, cả 8 nhận cùng `transactionId`, 7 lần là replay** |

**Lệch thiết kế ban đầu**, đã ghi lý do trong api-contract §4:
- Không dùng filter và trạng thái `IN_PROGRESS`.
- Không trả 409 `request-in-progress`. Request thứ hai **chờ** rồi replay kết quả của request đầu.

## 2. Tại sao

Mạng di động hay bị timeout. Client không biết request đầu đã trừ tiền hay chưa nên gửi lại. Nếu không có idempotency, tiền bị trừ 2 lần.

Điểm then chốt là **key phải commit cùng transaction với việc trừ tiền**. Nếu lưu ở 2 transaction riêng (thiết kế filter cũ), app chết đúng khoảng giữa sẽ dẫn tới:
- tiền đã trừ nhưng key chưa lưu, nên lần gửi lại **trừ lần nữa**; hoặc
- key kẹt ở `IN_PROGRESS` mãi mãi.

Filter nằm ngoài ranh giới transaction nên không giải quyết được chuyện này.

## 3. Kiến thức cốt lõi

| Khái niệm | Ý chính |
|---|---|
| Idempotent | Gọi N lần cho cùng kết quả như gọi 1 lần. GET/PUT/DELETE vốn idempotent theo đặc tả HTTP; POST thì không, nên cần key |
| Giữ chỗ bằng unique index | T1 `INSERT` key nhưng chưa commit. T2 `INSERT` cùng key sẽ **bị chặn** ở khóa chính. Khi T1 commit, T2 không chèn được gì và replay. Khi T1 rollback, T2 chèn thành công và tự làm việc |
| Tương tác với retry | Lần thử bị xung đột version thì rollback, kéo theo dòng key. Request trùng đang chờ sẽ được làm thay, rồi lần thử lại của request gốc sẽ replay kết quả đó. Tiền vẫn chỉ trừ 1 lần |
| `Propagation.MANDATORY` | Biến một **giả định** ("phải chạy trong transaction") thành **lỗi ngay lập tức** nếu bị vi phạm |
| Request hash | So sánh nội dung request: cùng key mà khác nội dung là lỗi phía client, không được lặng lẽ trả kết quả cũ |

## 4. Cách khác và trade-off

| Cách | Ưu | Nhược |
|---|---|---|
| **Giữ chỗ trong cùng transaction** (đã chọn) | Đúng tuyệt đối; request trùng nhận cùng kết quả | Request trùng giữ 1 DB connection trong lúc chờ (vài ms) |
| Filter + `IN_PROGRESS` ở transaction riêng | Dùng chung cho mọi endpoint | Có khoảng hở khi app crash; client phải xử lý 409 |
| Redis `SET NX` + TTL | Nhanh, không chạm DB | Redis và DB không chung transaction nên vẫn có khoảng hở; thêm hạ tầng |
| Unique constraint nghiệp vụ, ví dụ `transactions(client_request_id)` | Đơn giản | Không replay được response; mỗi bảng phải tự làm |
| Lưu cả response lỗi (cách của Stripe) | Lần gửi lại luôn nhận đúng lỗi cũ | Lỗi tạm thời (thiếu số dư) bị "đóng băng" 24 giờ |

## 5. Lỗi hay gặp

1. **Lưu key sau khi commit:** mở ra khoảng hở gây trừ tiền 2 lần.
2. **Hash JSON thô của request:** `85000` khác `85000.00`, khác thứ tự field, nên request giống hệt bị báo "khác". Phải chuẩn hóa trước khi băm.
3. **Key dùng chung toàn hệ thống, không theo user:** user A đoán được key của B và nhận response chứa dữ liệu của B. Đây là IDOR.
4. **Truyền `Instant` thẳng vào pgjdbc:** driver không hỗ trợ, phải đổi sang `OffsetDateTime`.
5. **Cạm bẫy gặp hôm nay:** extension Java của VS Code (trình biên dịch Eclipse) cũng ghi class vào `target/`. Khi test lỗi khó hiểu, chạy `mvnw clean verify`.

## 6. Câu hỏi phỏng vấn

1. Idempotency key là gì? Vì sao POST cần nó mà PUT thì không?
2. Bạn lưu key ở đâu, và lúc nào? Nếu app chết giữa chừng thì sao?
3. Hai request cùng key đến cùng lúc thì hệ thống của bạn xử lý thế nào?
4. Exactly-once delivery có tồn tại không? Idempotency liên quan gì đến at-least-once?
5. Request đầu thất bại thì có nên lưu kết quả lỗi không? Trade-off là gì?
6. Key nên hết hạn sau bao lâu? Dọn dẹp key thế nào khi chạy nhiều instance?

## 7. Bài tập nhỏ

Thử thay đổi thứ tự trong `IdempotencyStore.run`: gọi `work.get()` **trước**, rồi mới `INSERT ... ON CONFLICT DO NOTHING`, và nếu không chèn được thì ném exception để rollback.
- Chạy `sameIdempotencyKeyInParallel_paysOnce...`: test còn xanh không?
- Đếm xem có bao nhiêu lần `work` chạy thừa rồi bị rollback.
- Giải thích vì sao cách "làm trước, giữ chỗ sau" vẫn **đúng** nhưng tốn tài nguyên hơn, và nó gây hại gì nếu `work` gọi ra dịch vụ bên ngoài (ví dụ gửi email).
