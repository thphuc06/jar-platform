| Thí nghiệm | Kết quả |

## 2. Tại sao

- **Optimistic locking thay vì `SELECT FOR UPDATE`:** một user hiếm khi ghi từ 2 nơi cùng lúc, nên xung đột hiếm, và không cần giữ khóa khi chưa chắc có tranh chấp.
- **Retry phải bọc bên ngoài transaction:** transaction đã gặp lỗi version thì không dùng lại được. Lần thử mới phải là **transaction mới** để đọc được số dư mới. Vì vậy một khoản chi bị retry có thể trả 422 thiếu số dư, và đó là kết quả đúng.
- **FK kép và trigger:** nếu code có bug (quên kiểm tra `userId`, lỡ UPDATE sổ cái) thì DB vẫn chặn được. Trong fintech, sổ cái phải đúng kể cả khi code sai.

## 3. Kiến thức cốt lõi

| Khái niệm | Ý chính |
|---|---|
| Lost update | T1 và T2 cùng đọc version 7. T1 ghi lên version 8. Câu `UPDATE ... WHERE version = 7` của T2 khớp 0 dòng, Hibernate báo lỗi optimistic lock, và lần thử đó rollback |
| READ COMMITTED + `@Version` | Câu UPDATE của T2 **chờ** T1 commit, rồi đánh giá lại `WHERE` trên dòng mới. Vì vậy không cần isolation level cao hơn |
| Deadlock | T1 khóa A rồi chờ B, đúng lúc T2 khóa B rồi chờ A. Cách chữa tận gốc là **khóa theo cùng một thứ tự**: `order_updates` sắp các UPDATE theo khóa chính. Retry chỉ là lưới an toàn |
| `ConcurrencyFailureException` | Lớp cha chung của lỗi optimistic lock và deadlock. Mình chỉ retry lớp này, còn lỗi nghiệp vụ thì trả ngay |
| `Persistable` | Entity tự gán id mà không có `@Version` thì `save()` gọi `merge` và tốn thêm một câu SELECT. Implement `isNew()` để Spring Data gọi `persist` |
| Lý do `flush()` | Đẩy các câu UPDATE có kiểm tra version xuống DB ngay bên trong lần thử, thay vì đợi lúc commit |

## 4. Cách khác và trade-off

| Cách | Ưu | Nhược |
|---|---|---|
| **`RetryTemplate` tường minh** (đã chọn) | Nhìn code là thấy ranh giới retry/transaction, không phụ thuộc thứ tự proxy | Code dài hơn một chút |
| `@Retryable` (Framework 7) đặt trên một bean bọc bean `@Transactional` | Khai báo gọn | Phải tách 2 bean; đặt chung 1 method thì dễ sai thứ tự proxy |
| `SELECT ... FOR UPDATE` (pessimistic) | Không cần retry, dễ hiểu | Giữ khóa lâu hơn; vẫn có thể deadlock nếu khóa không theo thứ tự |
| `UPDATE jars SET balance = balance - ? WHERE balance >= ?` (atomic SQL) | Nhanh nhất, chỉ 1 câu lệnh | Logic nghiệp vụ nằm trong SQL; khó tính `balance_after` và sinh entry |

## 5. Lỗi hay gặp

1. **Retry bên trong `@Transactional`:** transaction đã bị đánh dấu rollback-only, nên retry vô ích.
2. **`@Digits(fraction = 0)` cho tiền:** sẽ từ chối `"85000.00"` vì `scale = 2`. Phải dùng `stripTrailingZeros()` như `@VndAmount`.
3. **Nhiều lệnh lỗi trong một test `@JdbcTest`:** sau lỗi đầu tiên PostgreSQL abort cả transaction. Mình đã gặp và phải tách test.
4. **Assertion đồng thời quá chặt:** mình đã viết sai `containsOnly(OK, CONFLICT)`, trong khi kết quả đúng là "tập con của" (`isSubsetOf`).
5. **Module test thiếu bean của module khác:** phải dùng `@MockitoBean IdentityApi`.
6. **Trả tiền dạng JSON number:** JavaScript dùng double nên làm tròn mất. Phải trả string.

## 6. Câu hỏi phỏng vấn

1. Optimistic và pessimistic locking khác nhau ra sao? Khi nào chọn cái nào?
2. Vì sao READ COMMITTED đủ dùng khi đã có `@Version`? Nếu chuyển sang REPEATABLE READ thì PostgreSQL làm gì khác?
3. Deadlock xảy ra thế nào và cách phòng tránh? Vì sao không nên chỉ dựa vào retry?
4. Vì sao retry phải tạo transaction mới? Cần retry những exception nào?
5. Vì sao không dùng `double` cho tiền? `BigDecimal.equals` khác `compareTo` ra sao?
6. Làm sao bảo đảm sổ cái không bị sửa? Bạn kiểm tra bất biến số dư thế nào?
