## 2. Tại sao
Phase 1 sẽ thêm 4 module (identity, ledger, goals, budgeting). Luật phải có **trước** khi viết code, vì sửa lỗi ranh giới module khi đã có 10.000 dòng thì cực kỳ tốn kém. Tương tự, format thống nhất ngay từ đầu giúp mỗi PR chỉ chứa thay đổi thật, không lẫn thay đổi do format.

## 3. Kiến thức cốt lõi
- **Spring Modulith dựa trên ArchUnit.** Nó đọc bytecode của các class rồi dựng đồ thị: package con trực tiếp của package gốc là một module; class nằm ngay ở package gốc của module là API public; mọi package con là *internal*. `verify()` fail khi có **vòng phụ thuộc** hoặc **truy cập vào internal** của module khác.
- **Vì sao không dùng `public`/`private` của Java?** Java chỉ giới hạn được truy cập trong cùng package. Class trong `ledger.internal.repo` phải `public` thì `ledger.internal.service` mới gọi được, và khi đó **mọi module khác** cũng gọi được. Modulith bổ sung lớp kiểm soát ở cấp "nhóm package". (JPMS cũng làm được, nhưng nặng nề với Spring.)
- **"Test của test":** nếu `ApplicationModules.of(...)` quét nhầm package hoặc không import class nào thì `verify()` vẫn xanh. Fixture cố ý vi phạm chứng minh cơ chế thật sự hoạt động. Fixture dùng `ImportOption` có import cả class test, vì mặc định Modulith **bỏ qua** class test.
- **Thứ tự BOM** (đúng câu hỏi bài tập P0.5): trong `dependencyManagement`, BOM **import trước thắng**. BOM của Spring Cloud AWS tự import Modulith 2.1.0, nên Modulith **âm thầm** bị hạ version. Không có lỗi, không có cảnh báo; chỉ `dependency:tree` mới cho thấy.
- **Spotless + palantir:** formatter có tính tất định, cùng input luôn ra cùng output. `check` gắn vào `verify`, nên CI fail nếu bạn quên `apply`.

## 4. Cách khác & trade-off
| Cách | Trade-off |
|---|---|
| ArchUnit thuần (tự viết rule) | Linh hoạt hơn nhưng phải tự viết mọi rule; Modulith có sẵn quy ước + event registry + test module |
| Multi-module Maven (mỗi module nghiệp vụ một artifact) | Ranh giới được trình biên dịch kiểm tra, nhưng build và refactor nặng hơn, quá mức cần thiết khi có 1 người làm |
| Checkstyle | Chỉ *báo* lỗi style chứ không *tự sửa*; Spotless tự format nên đỡ tranh cãi |
| google-java-format | Thụt lề 2 space; palantir giống GJF nhưng 4 space và 120 cột, dễ đọc hơn với code Spring nhiều chuỗi lệnh |

## 5. Lỗi hay gặp
- Đặt class nghiệp vụ ngay ở package gốc `io.github.thphuc06.jars`. Modulith không coi đó là module nào, nên ranh giới bị vô hiệu.
- Dùng `@Autowired` một repository của module khác. `verify()` sẽ báo; cách sửa là gọi qua `XxxApi` hoặc dùng event.
- Thêm BOM mà không kiểm tra `dependency:tree`, dẫn tới version bị BOM khác "đè" mà không biết.
- Quên chạy `spotless:apply` → `verify` fail (đây là hành vi mong muốn).

## 7. Bài tập nhỏ
1. Tạo tạm module `src/main/java/.../jars/demo/` gồm `DemoApi.java` (ở root package) và `internal/DemoRepo.java`. Trong `platform`, inject `DemoRepo`. Chạy `./mvnw verify`, đọc thông báo lỗi của Modulith, rồi sửa lại cho đúng luật (gọi qua `DemoApi`). Gợi ý: `platform` là shared module, nhưng shared **không** có nghĩa là được phép phụ thuộc ngược vào module nghiệp vụ.
2. Mở `target/spring-modulith-docs/components.puml` bằng PlantUML (extension VS Code hoặc plantuml.com) và xem diagram.
3. **Xóa module `demo`** trước khi commit.
