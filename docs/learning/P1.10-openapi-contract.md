# P1.10: OpenAPI contract sinh từ code và TypeScript client

> Ghi chú học tập của bước P1.10 (2026-10-27). Kết quả và bối cảnh của bước nằm ở [roadmap](../06-plan/roadmap.md); quyết định ghi ở [ADR-0019](../04-adr/0019-code-first-openapi-contract.md); quy ước 7 mục ở [README](README.md).

## 1. Đã làm gì

| Phần | Nội dung |

## 2. Tại sao

- **UI cần type đúng chứ không chỉ cần "có type".** Spec mà springdoc sinh thô có 7 lỗi (bảng dưới). Sinh TypeScript từ spec đó thì client còn sai hơn viết tay, vì người dùng tin type.
- **Một nguồn sự thật, máy đọc được.** api-contract.md giải thích quy ước cho người đọc. File YAML là thứ build của `web` dùng, và mỗi thay đổi API hiện ra thành diff trong commit.
- **Tài liệu chỉ có giá trị khi được test.** Test so file chỉ bắt được trường hợp "quên sinh lại file". Test so với filter chain và với response thật mới bắt được trường hợp "spec sai ngay từ đầu".

| # | Spec thô của springdoc | Đã sửa bằng |
|---|---|---|
| 1 | `ErrorProbeController` (code test) lọt vào spec | `@Hidden` |
| 2 | `operationId` là `list`, `list_1`, `get_1`, `create_1` (hậu tố phụ thuộc thứ tự scan) | Đặt tên method duy nhất + test |
| 3 | Mọi response là `'*/*'` | `springdoc.default-produces-media-type: application/json` |
| 4 | POST tạo mới ghi `200`, DELETE ghi `200` | `@ResponseStatus(CREATED / NO_CONTENT)` |
| 5 | Không có security scheme, không mô tả lỗi | `ApiContractRules` + `Problem` |
| 6 | Mọi field của response đều optional, không field nào nullable | `required` cho response + `@Nullable` → nullable |
| 7 | **Tiền trong request là `type: number`** | `@VndAmount` → `string` + `pattern` |

## 3. Kiến thức cốt lõi

| Khái niệm | Ý chính |
|---|---|
| springdoc hoạt động thế nào | Đọc các handler từ `RequestMappingHandlerMapping`, rồi dùng swagger-core (`ModelResolver`, dựa trên thông tin bean của Jackson) để dựng schema. Có 3 điểm móc: **`ModelConverter`** cho từng kiểu Java, **`OperationCustomizer`** cho từng handler, **`OpenApiCustomizer`** cho cả tài liệu |
| `required` ≠ non-null | `required` nghĩa là **key luôn có mặt**; nullable nghĩa là **giá trị có thể là `null`**. Bốn tổ hợp trong TypeScript: `a: T`, `a: T \| null`, `a?: T`, `a?: T \| null`. Jackson mặc định ghi cả field `null` (`Include.ALWAYS`), nên response của mình là `required` (+ nullable nếu có `@Nullable`) |
| OpenAPI 3.0 vs 3.1 | 3.1 dùng đúng JSON Schema 2020-12: `nullable: true` của 3.0 bị bỏ, thay bằng `type: [string, "null"]`. Enum có thể null phải có `null` **trong `enum`**, nếu không giá trị `null` vẫn sai theo JSON Schema |
| Annotation TYPE_USE vs declaration | JSpecify `@Nullable` có `@Target(TYPE_USE)`: nó gắn vào **kiểu** (`AnnotatedType`), không gắn vào field. `field.isAnnotationPresent(Nullable.class)` trả `false`, còn `field.getAnnotatedType().isAnnotationPresent(...)` trả `true`. swagger-core chỉ đọc loại thứ nhất. Bằng chứng: `CategoryView.defaultJarCode` có `@Nullable` từ P1.4, nhưng spec thô vẫn ghi field đó là không null |
| Tiền là string | `number` trong JS là IEEE 754 double, chỉ biểu diễn chính xác số nguyên tới 2^53 ≈ 9,007·10^15 (16 chữ số), trong khi `@VndAmount` cho tới 17 chữ số. Server vẫn nhận cả `85000` lẫn `"85000"` (Jackson tự chuyển), nhưng contract chỉ hứa string |
| `default` response | Mô tả "mọi status không được liệt kê". `openapi-fetch` dùng nó làm kiểu của `error`, nên `error.type` và `error.traceId` có type ngay |
| Scope trong security requirement | Ở OpenAPI 3.1, scheme không phải OAuth2 (ở đây là `http bearer`) cũng được ghi danh sách "role" trong requirement, nên ghi được `bearerAuth: [jars-api/read]` mà không cần URL Cognito (URL này khác nhau theo môi trường) |
| Server tương đối | `servers: [{url: /}]`: client gọi cùng origin (Vite proxy ở local). Spec không chứa host nào, nên file không đổi theo môi trường |

## 4. Cách khác và trade-off

| Cách | Ưu | Nhược |
|---|---|---|
| **Code-first + commit file + contract test** (đã chọn) | Một nguồn (code); diff API hiện trong commit; test bắt spec sai | Tên method trở thành một phần của contract; mỗi operation mới phải có ví dụ trong test |
| Design-first (viết YAML trước, `openapi-generator` sinh interface Spring) | Thống nhất được contract trước khi có code; hợp với nhiều team | Code sinh ra khó đọc; validation và nghiệp vụ vẫn phải viết tay; hai nguồn phải khớp nhau |
| `@Schema` / `@Operation` / `@ApiResponse` trên từng method | Phổ biến, dễ tra | Lặp lại 18 lần; quên một chỗ là spec sai mà không ai biết |
| `springdoc-openapi-maven-plugin` | Không cần viết test | Phải khởi động app thật với DB trong Maven; chỉ sinh file, không kiểm tra gì |
| Consumer-driven contract (Pact, Spring Cloud Contract) | Kiểm tra theo đúng nhu cầu của từng client | Nặng hơn nhiều; đáng làm khi có nhiều client hoặc nhiều team |
| `openapi-generator` (typescript-fetch) cho client | Sinh sẵn class và hàm | Nhiều code runtime; khó tùy biến. `openapi-typescript` chỉ sinh type (0 byte runtime), còn `openapi-fetch` khoảng 6 kB theo README của nó (file `index.mjs` chưa minify là 17 kB) |
| `orval` | Sinh sẵn hook TanStack Query | Thêm một lớp phụ thuộc; ở P1.11 tự bọc `openapi-fetch` cũng chỉ vài dòng |

## 5. Lỗi hay gặp

1. **`/v3/api-docs` trả 401.** `anyRequest().denyAll()` chặn mọi path không có trong danh sách. Phải `permitAll` cho path của tài liệu và **tắt springdoc ở prod**: path vẫn được permit nhưng không còn handler, nên trả 404.
2. **Code của test lọt vào contract.** `ErrorProbeController` nằm trong `src/test` nhưng vẫn được scan khi chạy test → `@Hidden`.
3. **Tin rằng springdoc hiểu `@Nullable`.** Với JSpecify (TYPE_USE) thì không. Phải tự đọc `getAnnotatedType()` trong một `ModelConverter`.
4. **Enum có thể null mà quên thêm `null` vào `enum`.** Validator JSON Schema sẽ coi giá trị `null` là sai dù `type` đã có `"null"`.
5. **`operationId` tự động (`list_1`).** Hậu tố phụ thuộc thứ tự scan: thêm một controller là ID của controller khác có thể đổi. Client nào dùng `operationId` sẽ vỡ.
6. **`ResponseEntity.created(...)` không cho springdoc biết status 201.** Status đó chỉ có lúc chạy, nên phải khai báo `@ResponseStatus`.
7. **Một record dùng cho cả request lẫn response.** Response cần "luôn có mặt", còn request cần "không bắt buộc", nên `required` không thể đúng cho cả hai phía. `ApiContractRules` ném lỗi ngay khi gặp trường hợp này.
8. **(Gặp thật)** Class do Eclipse compiler trong VS Code sinh vào `target/` gây "Unresolved compilation problems". Lỗi thật là lambda dùng biến không effectively final; chỉ thấy được khi chạy `mvnw clean`.

## 6. Câu hỏi phỏng vấn

1. Code-first và design-first cho API khác nhau thế nào? Khi nào chọn cách nào?
2. Làm sao biết tài liệu API (Swagger) không lệch so với code? Contract test, consumer-driven contract (Pact) và test so schema khác nhau ở đâu?
3. Phân biệt optional (không bắt buộc) và nullable trong JSON, OpenAPI và TypeScript. API của bạn trả field `null` hay bỏ hẳn field đó, vì sao?
4. Vì sao không gửi tiền dạng `number` trong JSON?
5. Có nên bật Swagger UI ở production không? Rủi ro là gì?
6. Thay đổi nào trên REST API là breaking change? (Thêm field vào response thì không; thêm field bắt buộc vào request thì có; cho một field response được phép `null` là breaking với client TypeScript.)
7. TYPE_USE annotation khác declaration annotation thế nào? Ví dụ nào trong Spring 7?

## 7. Bài tập nhỏ

1. Gắn `@JsonInclude(JsonInclude.Include.NON_NULL)` lên `TransactionItem`, chạy `OpenApiContractTest`, và **đoán trước** test nào fail với thông báo gì (gợi ý: mutant M6). Sau đó thử đổi `ApiContractRules` để field có thể null thành "không bắt buộc, không null" (`a?: T`), rồi so sánh hai kiểu type TypeScript: kiểu nào dễ dùng hơn ở UI?
2. Dùng `oasdiff` (`oasdiff breaking old.yaml new.yaml`) so bản contract trước và sau ba thay đổi: thêm một field vào `JarResponse`, xóa `note` khỏi `TransactionItem`, thêm một field bắt buộc vào `PostTransactionRequest`. Thay đổi nào bị báo breaking? Có nên đưa bước này vào CI không?
3. Trong `DtoSchemaConverter`, thay `oneOf: [$ref, {type: null}]` bằng `$ref` cộng `type: [object, "null"]` đặt cạnh nhau (OpenAPI 3.1 cho phép). Sinh lại type bằng `openapi-typescript`: kết quả có còn là `JarRef | null` không?
